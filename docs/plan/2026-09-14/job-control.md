## 2. 设计

### A. 权限收口(P0,先做)

- 先复现(AGENTS.md §5.1):管理员起一个后台命令,成员账号 `curl` 列表 / 日志 / 停止,确认三件都能做到。**复现不出来就回来改结论,不硬修。**
- 收口放在 `src/web/turns/` 的四个任务接口共用的一个判定函数里,不在每个接口各写一遍:
  - 管理员:全部可见、可停。
  - 成员:只看 / 只停**自己名下会话**的任务(`stores.owner_of_session`)。
  - 没有会话归属的旧任务:成员不可见。
- 与 `jobs::job_visible` 的会话口径保持一致,只是 HTTP 这一侧补上「账号」这一维。

### B. 任务侧栏视图

- 顶栏「任务」按钮,有运行中任务时带数字角标;打开右侧侧栏临时视图(与 `file-links.md` 等共用槽位)。手机上是全屏抽屉。
- 分组:**当前会话** / **其他会话**(后者仅管理员)。
- 每行:类型(子代理 / 后台命令 / 前台命令 / 遗留进程)· 标题 · 所属会话 · 已运行时长 · token(子代理)· 停止。
- 展开看日志 / 子过程,复用现有 `/log`、`/trace` 接口。
- 输入框上方任务条不动,继续做快捷入口;「后台任务 ×N」那一行加一个「全部」跳到侧栏视图。

### C. 前台命令单独停止

- 运行中的前台命令按 `tool_id` 登记一个取消句柄;新接口 `POST /api/runs/{run_id}/tools/{tool_id}/cancel`,权限同 A。
- 工具卡上加停止按钮,侧栏视图里同样列出。
- 停止后返回给模型的结果要说真原因:`stopped by the user after 47s`,附已产生的输出。不写成超时或失败——她会照着错误原因换个方式重试。
- 只停这一条命令,不取消整轮;她拿到结果后继续往下走。

### D. 遗留进程

前台命令正常结束后,进程组里还活着的进程(`&` 出去的开发服务器之类)现在没人管,也看不见。

- 命令结束时探测进程组是否还有成员;有就登记成一条「遗留进程」任务,出现在任务视图里,可停止。
- **不自动杀**:`npm run dev &` 这类是故意留着的。
- 明说做不到的:`setsid` / 双 fork 脱离进程组的守护进程追不到。视图底部写一句,不假装全都管住了。

### E. 停止的语义

- 进程组先 SIGTERM,等 3 秒,还在就 SIGKILL。`未核实`:现有 `stop_one` 是否已经是这样,施工时读一眼再决定改不改。
- 子代理停止沿用现有路径。

## 3. 理念对照

| 理念 | 落到这里 |
|---|---|
| 权限由代码承担 | 任务接口按真实账号与会话归属判定;前端的会话过滤只是显示,不是权限 |
| 报错要说真原因 | 被用户停掉的命令明说「用户停止」,不混成超时 |
| 先证明不修时现象出现 | A 先用成员账号复现越权;C 先证明现在停不了单条前台命令 |
| append-only | 停止结果作为正常工具结果进入账本;`未核实`:后台任务结束通知是怎么进上下文的,停止要走同一条路,不另开注入 |

## 6. 施工记录

### 步 1 权限收口(2026-09-14,未编译、未跑测试)

**根因(读码核实)**:四个接口只调 `require_auth`(`src/web/security.rs:477`,它就是 `require_identity` 丢掉身份);
注册表判定 `jobs::job_visible`(`src/tools/jobs/mod.rs:656`)只有会话一维,HTTP 请求没有「当前会话」,落进 `(None, _) => true` 全局可见。

**改动**

| 文件 | 改动 |
|---|---|
| `src/web/job_access.rs`(新) | `job_allowed` 纯判定 + `job_visible_to` / `require_job_access`;单测 `members_only_reach_jobs_in_their_own_sessions` |
| `src/web/mod.rs` | 模块声明 |
| `src/web/turns/mod.rs` | `GET /api/jobs` 按身份过滤行;`/log`、`/trace`、`DELETE` 先过 `require_job_access` |

**与设计不同的地方**

- 看不到的任务回 **404**,不是 §5 写的 403:403 等于向成员确认这个 id 存在。
- 归属口径直接复用 `stores.owner_of_session`,与事件流 `EventOwnerFilter`(`src/web/ownership.rs:37`)一致;没有另造「账号 + 会话」判定。
  但两者对「查不到归属的会话」处理一致(管理员放行、成员不给),对「任务没有会话」本处成员不可见。

**没验证的地方**

- 全部未编译;`cargo fmt` 未跑。
- §5.1 要求的「修前能复现」没做:单测是新纯函数,退回修复前不存在,守的是判定表而不是接口。接口级回归(成员 cookie 打四个接口)`src/web/tests/` 里没有现成的成员身份夹具,**待补**。
- 本机 IPC(`src/web/ipc_server.rs:126`)与 REPL(`src/cli/repl/`)仍列全部任务:只有本机进程能连,不在本步范围。

**验收流程**

1. `cargo build && cargo test --lib job_access`,重启 daemon。
2. 管理员账号起一个后台命令:让她 `run_command` 跑 `sleep 300` 并放后台,记下 job id(任务条里有)。
3. 用成员账号登录另一个浏览器(或无痕窗口),开发者工具控制台依次执行:
   - `await (await fetch("/api/jobs")).json()` → `jobs` 里**没有**那条任务。
   - `(await fetch("/api/jobs/<id>/log")).status` → `404`;`/trace` 同样 `404`。
   - `(await fetch("/api/jobs/<id>", { method: "DELETE" })).status` → `404`,管理员那边任务仍在跑。
4. 成员自己起一个后台任务:成员能看到、能读日志、能停;管理员也能看到并停掉它。
5. 管理员的任务条与停止按钮行为不变。
