# 2026-09-14 地图:坐标锚点优先,以及卡片没出现的那件事

> 承 `2026-09-13-gqy-personalization.md` §14。09-13 晚用户用真地址试了新地图工具,
> 提了两件事:(1) 地图交互「似乎不在工具圈外面,默认是结尾的那个纯文字」;
> (2) 文本地址检索在城中村/自编门牌/本地俗称上会漂,应该改用经纬度锚点。
>
> 第二件是对的,但**它在用户举的例子里的量级不是 700 米,是 135 米**——先看数字。

## 1. 实测(09-13 晚,daemon 已是新版)

> **地址已隐去。** 用户拿自己家那片城中村试的,下面用 `<小区>` / `<自编门牌>` /
> `<俗称地名>` 代指;结论与数字都是真的,只是定位信息不写进仓库(理由见 §8)。

```
$ miyu tool-call map_search '{"query":"<小区>","city":"<市>","limit":3}'
count=1  <小区>  (一个点,村子质心)

$ miyu tool-call map_search '{"query":"<小区><自编门牌>","city":"<市>"}'
count=1  <小区>  ← 与上面**同一个点**,自编门牌被整段忽略

$ miyu tool-call map_search '{"query":"<俗称地名>","city":"<市>"}'
count=0  nothing matched
```

用户另外给了一个他自己测出来的经纬度锚点(来自高德,GCJ-02)。

| 对比 | 距离 |
|---|---|
| OSM 文本检索结果(WGS-84)↔ 用户锚点 | 710 m |
| 同一结果换算成 GCJ-02 后 ↔ 用户锚点 | **135 m** |

### 1.1 最重要的一条结论:锚点不记坐标系就是陷阱

用户那个锚点几乎一定来自高德/腾讯,也就是 **GCJ-02**。把它和 OSM 的 WGS-84 数字
直接相减,得到的 710 米里有 **575 米是坐标系差**,只有 135 米是真正的文本匹配漂移
(村子质心 vs 某栋自建房)。

这不推翻「用坐标锚点」的结论——135 米在城中村里照样是走错巷子的量级,而且
`C094` 被整段忽略这件事实测坐实了。但它改变了锚点功能该长什么样:

> **一个不带坐标系标注的经纬度,是一颗定时炸弹。** 粘进另一套地图就稳定偏
> 五百米,而且地图本身看起来完全正常——正是 09-13 §14.2 花力气防的那个错,
> 只不过这次是从用户那一侧进来的。

所以下面所有涉及锚点的设计,**datum 是必填字段**,不是可选备注。

## 2. 用户提供的原理(整理)

两种定位模式的差异:

- **文本地址检索**:输入字符串,地图引擎与已录入的 POI 点、官方民政门牌做模糊
  匹配。城中村的自编门牌是村民内部编号,不在民政门牌库;「某某广场」「社区奶站」
  这类是本地俗称,不是标准化地名。库里没有绑定关系,于是**就近匹配**一个近似
  地点——漂移就是这么来的。
- **经纬度检索**:坐标是绝对位置,不依赖任何文字名称,直接渲染到点位,不受俗称
  与自编门牌缺失影响。

经纬度的短板同样要记住:**没有语义**,不适合给人念。所以正确形态是
**坐标做锚、文字做注**:坐标负责锁点,文字(「某某广场西 150 米、奶站旁」)
负责人到现场后的二次核验。

## 3. 设计(按优先级)

### A. 坐标直接进 `query`(小,先做)

现在只有 `reverse` 参数接受坐标,模型不一定想得起来用。改成:`query` 本身长得像
一对经纬度时,**不走文本检索**,直接当锚点渲染,并顺手逆地理编码取一个人类可读
的描述当备注。

要连 datum 一起吃:一串裸经纬度默认按哪套算?**必须显式**——
加一个 `datum` 参数(`gcj02` / `wgs84`),缺省按当前 provider 的原生 datum,
并在返回体里回显用的是哪套,让卡片能标出来。

### B. 锚点库(核心)

用户的原话是「优先使用预先录入的经纬度锚点」。落成一件可存可查的东西:

| 项 | 内容 |
|---|---|
| 存 | 名字(可多个别名)+ 坐标 + **datum** + 文字备注 + 存入时间 |
| 落点 | 仿 `album`:按人格分库,`home/<用户>/places/<人格>/index.json` |
| 查 | `map_search` 先查锚点库(精确名/别名/子串),命中就直接出结果、**不碰外部源** |
| 写 | 工具动作 `save_anchor`;卡片上也给一个「把这个点存成锚点」的按钮 |

命中锚点时卡片要明确标出「来自你的锚点库」,而不是混在检索结果里——这两者的
可信度完全不同。

### C. 双源交叉校验(利用我们已经有两条源这件事)

用户的判据是「同一地点在多种地图上搜出来不一致,就说明不可信」。我们正好两条源
都在:同一查询两边都问一次,**换算到同一 datum 后**比距离,超过阈值(建议 200 m)
就在卡片上写一句:

> 两个数据源给的位置差 340 米,这类自编门牌/俗称地名容易匹配漂移;建议用坐标锚点。

代价是每次两倍请求。折中:只在**文本检索且结果只有一条**时做交叉校验(那正是最
容易「就近匹配」蒙混过关的情形),或者加一个开关默认开。

### D. 契约措辞(改 `descriptions/map.json`)

写进工具描述,让她在**调之前**就分流:

- 地址里带疑似自编编号(`C094` 这种字母加数字、`3 栋 2 单元`这类非官方门牌)或本地俗称
  (广场、奶站、某某超市旁)时,**不要把整段文本丢给地址解析**。
- 先问锚点库;没有就把地址拆成「能匹配的部分(小区/路名)」+「只给人看的部分」,
  只把前者送检索,后者原样写进卡片备注。
- 结果只有一条且用户给的是自编门牌时,要在回答里说明「这是小区级定位,不是那栋
  房子」,而不是把村子质心当成门牌。

### E. `count=0` 也该出卡

现在没结果就不画卡(`parse()` 返回 null),于是屏幕上只剩她自己那句话——用户
09-13 晚看到的「默认是结尾的那个纯文字」大概率就是这个。改成画一张小卡:说清
没匹配到、给出「换个说法 / 直接给坐标 / 存成锚点」三条出路。

## 4. 卡片侧

- 坐标做主、文字做注:坐标行已经有「复制」,再加「存成锚点」。
- datum 标签:卡片上明写这组坐标是 GCJ-02 还是 WGS-84。**别让人从卡片上抄一个
  没有标注的坐标去别处用**——那正是 §1.1 那颗炸弹的引信。
- 来源徽标:锚点库命中 / 检索结果,两种要一眼能分。

## 5. 卡片位置:进收起区(09-13 晚用户拍板,已改)

原来挂在工具签外面(与待办、分享附件同一档:收起态也看得见)。用户裁定改成挂进
`.tool-body`,跟着工具签一起收起——**这是隐私判断,不是布局偏好**:

> 一张地图钉的是现实里的一个点——家、常去的店。默认摊在气泡里,截图、投屏、
> 旁边有人时全躲不掉,而它并不是每次都要看的东西。默认藏起来、要看点一下,
> 代价小得多。

`web/app.js` 的 `TOOL_RICH_CARDS` 因此多了一位 `mount`:`fold`(进收起区)/
`outside`(挂外面)。地图走 fold,快递暂时仍是 outside——**这条待定**:物流轨迹
带网点与城市,能推出住址,按同一条理由它也该进 fold。等用户一句话。

顺带把 `.map-card` 从 `WIDE_BLOCK_SELECTOR` 里摘了:它现在活在收起区里,展开态
已经由 `.tool-card:not(.collapsed)` 顶着,再留一条会让收起态的气泡也白撑宽。

## 6. 待确认

1. 快递卡片要不要跟着进 fold(见 §5)。
2. 锚点库要不要跨人格共享?(图库是分库的;但「我家在哪」这种事,换个人格就不
   知道了,说不过去。倾向:锚点库**不分人格**,与图库口径不同,理由写进代码注释。)

## 7. 不做的

- 不接百度地图:再多一套 BD-09 坐标系,换算链路从两条变三条,收益只有「又一个
  文本检索源」——而我们刚认定文本检索本身就是问题所在。
- 不做路线规划/导航。用户没提,而它会把这件工具从「查一个点」拉成一个地图应用。

## 8. `GQY.md` 会不会被人格会话读到(09-13 晚排查:不会,但有两个相邻的坑)

用户的疑问:`/init` 生成的 `GQY.md` 会不会让顾清影的人格会话总往那儿找。

**注入面上不会。** 读它的只有两处,都卡在 dev:`agent::prompt::mode_system_prompt`
的 `AgentMode::Dev` 分支,以及 `subagent.rs` 里 `dev == true` 才走的
`build_dev_system_prompt`。人格会话走 `system_prompt_with`,里面一个字都没有。

**而且她的工作区不在这个仓库。** 会话库 693 个回合的 workspace 分布:
`/Users/mac` 491、`/Users/mac/Desktop/Miyu` 19、`…/Projects/GQY/kb` 9,没有一条是
本仓库。注入按工作区根找文件,她那边找的是 `~/GQY.md`——不存在。

### 8.0 现状裁定:注入方式改掉之前,`/init` 先不用(09-13 晚用户拍板)

量出来的对比是决定性的:dev 提示词本体 **45 字节**(`You are a helpful software
engineer assistant.`,极简是有 08-15 实测背书的刻意选择),而 `/init` 生成的
`GQY.md` 是 **10 KB**——等于在一个刻意压到一行的提示词前面糊了 220 倍于它的散文,
而且**没有任何 A/B** 说明这样更好。叠加它进的是**缓存前缀**(这个仓库的核心纪律
恰恰是前缀逐字节稳定),以及仓库里已经有一份 8 KB 的 `AGENTS.md` 在讲同一批事。

**裁定**:在注入方式改掉之前不用 `/init`,也不在任何 dev 工作区根上留
`GQY.md`(留着就会被注入)。今晚生成的那份已删。

**改法(明天):**

1. 注入全文 → 注入**一句指路**:「项目约定在 `AGENTS.md`,动手前先读」。前缀从
   10 KB 变成约 30 token;文件改了不再掰断缓存;她读到的永远是当下那份,过时问题
   自然消失。
2. `/init` 认已有的约定文件:有 `AGENTS.md` 就更新它,没有才新建——**一个仓库
   只该有一份项目约定文件**,两份迟早漂移且没人规定听谁的。
3. 约定文件住在磁盘上,不住在前缀里。这条是规矩,不是这一次的权宜。

### 8.1 坑一:`/init` 会往家目录写文件

491 个回合的工作区是 `/Users/mac`。在那种会话里敲 `/init`,文件会落在**家目录**,
而且从那以后每个以家目录为工作区的 dev 会话都会把它当项目上下文注入。家目录不是
项目。**待做**:`/init` 在写之前判断工作区像不像一个项目(有没有 `.git` /
`Cargo.toml` / `package.json` 之类),不像就拒绝并说清楚,别默默写。

### 8.2 坑二:文件名会误导

`GQY.md` 读起来像「顾清影的文件」,实际是项目工作备忘,与人格无关。它现在不在她
视线里,但哪天落到她能看到的目录里,按名字猜内容的概率不低。**待定**:是否换成
与人格无关的名字(`PROJECT.md` / `MIYU.md`),还是保留 `GQY.md` 但在文件头写明
「这是项目备忘,不是人格材料」。倾向后者——换名要动 `PROJECT_CONTEXT_FILE`
常量与已生成的文件,收益只是少一次误会。

### 8.3 顺带要确认的

她的人格会话跑在 antigravity(agy)中转里,而 agy 自己有「从 cwd 自动读上下文
文件」的惯例(`GEMINI.md` 一类)。`GQY.md` 不在那套名字里,所以不受影响;但如果
哪天把她的工作区指到本仓库,agy 可能会自动读走仓库根上的 `AGENTS.md`——那份是
写给「开发这个项目的 agent」看的,不该进人格会话。**没验证,写在这里备查。**

## 9. 为什么这份文档里没有具体地址

原稿里写着用户家那片城中村的名字、自编门牌和一组经纬度——当技术实例写的,没想
它同时是一个人的住址。**文档会跟着 git 走**,推到远端就留在历史里;删文件不等于
删历史,要重写才算数。所以这里一律用占位符,数字(710 m / 135 m / 575 m)留着,
因为它们脱离坐标之后不指向任何地方。

同一条规矩对以后的实例也成立:调试用真实地址没问题,**写进仓库的那一份要换掉**。
